# 首批商家交付、签收与回访单

适用于单商家一次性交付。请复制本文件为每家商家的独立记录，以匿名编号管理；不要把填写后的真实商家记录、密码、客户名单或完整备份提交到源码仓库。

本模板不代表已经签收或付款。首次配置、示例清理、复制报价、主动更新资料、自动日备份和备份列表，须由发行负责人按当前版本实际验收后勾选。不能在尚未实现或尚未验证时勾选通过。

## 安装前预检

- [ ] 已确认是一家商家的独立环境，不与其他项目或其他商家共用数据目录。
- [ ] 电脑、Node.js 24 或 Docker、可写磁盘和可用端口符合当前发行要求。
- [ ] Node 安装方式已执行 `npm run doctor`，核对每项结果并处理失败项；明确跳过的端口检查不计作通过。Docker 方式按部署说明单独核对。
- [ ] 已确认同一 Wi-Fi 可互相访问，防火墙允许专用网络连接；访客网络隔离不影响测试。
- [ ] 真实手机将参与验收；未把 Chromium 手机模拟结果当成真实 iPhone / Android 验证。
- [ ] 商家理解电脑关机、睡眠、断网后手机会无法访问，局域网地址可能随网络改变。
- [ ] 如使用已有远程服务器，已另行确认 HTTPS、访问密码、持久卷、维护责任和费用；没有擅自购买或公开发布。
- [ ] 已获得安装与必要操作授权；演示及安全策略测试使用独立虚构资料。

本机启动与手机连接步骤见 [PHONE-DEMO.md](PHONE-DEMO.md)。安装前可先执行项目的自动化检查，但自动化不能代替商家自己的设备验收。

## 首次配置与正式资料切换

1. 填写商家名称、联系人、电话、地址和报价条款，逐项核对 PDF 将显示的内容。新演示商家默认采用中性条款，不直接继承演示中的“含税”或预付款承诺；旧版已使用商家的现有资料和条款会保留供核对。
2. 向商家说明演示客户与正式客户的区别。只有系统具有可靠来源标记、且未被用户修改或用于真实记录的样例，才能按已验收规则清理。
3. 旧版本已有记录没有来源标记时，应保留为未分类记录；不能按客户名字判断并自动删除。若商家希望完全空白开始，可使用新的独立数据目录。
4. 如确需清空全部数据，先导出并核对备份，让商家查看将被清空的范围，再由商家输入产品要求的确认文字。备份未成功，不执行清空。
5. 在正式资料上不做破坏性“清空测试”。样例保护、清理和恢复行为应在独立演示环境中验收。

## 每天的备份操作

自动日备份保存在服务端，同一设备损坏时仍可能一并丢失，因此商家每天营业结束后还需执行以下操作：

1. 在“商家设置”的备份区域手动导出当前数据，或下载已经核对日期的最新备份。文件名建议包含日期和商家匿名编号。
2. 确认浏览器下载完成、文件非空，并复制到另一设备、商家自己管理的移动存储或既有安全存储位置。不要只留在运行服务的同一磁盘。
3. 在备份登记中记录日期、文件名、异机位置和操作人；无需把备份内容发给安装人员。
4. 每周核对一次最近备份是否完整；重大修改、恢复和升级前另外导出一份，不覆盖原来的唯一副本。

自动备份只能在服务运行期间执行；关机时不会执行计划。具体当日补齐逻辑、保留天数或份数，按本次发行填写到交付单。若产品提示备份失败，应先保留现有数据，联系安装人员处理，不反复清空或恢复。

## 恢复步骤

1. 先停止继续录入，说明恢复会替换当前资料。优先在独立临时数据目录或测试容器中验证备份。
2. 先导出当前状态，并保留产品生成的恢复前副本；核对准备恢复的文件、商家、导出日期和记录数量。
3. 使用产品恢复入口上传或选择备份。文件校验失败时停止操作，不修改 JSON 来绕过金额、关联或版本检查。
4. 确认替换后，核对至少一位客户、一份报价的金额与 PDF，以及状态、下次跟进日期和历史记录。
5. 重启服务后再查一次，确认无误后恢复录入，并将恢复后的数据重新导出到异机位置。

导入文件大小和备份版本有产品限制，具体以上述交付版本为准。备份格式不兼容时先由安装人员评估；不要让旧版本直接打开已升级的数据库，也不要混拷 SQLite 的不同版本文件。

## 升级与回滚

升级前安排短暂维护时间，记录旧版 Git 提交或源码包，并确认能找到对应启动方式。不要只保留一份被新版本覆盖的源码。

**升级前：**

1. 导出一份由旧版本生成的 JSON，并在独立环境验证可恢复；这份文件用于必要时回到旧版。
2. 停止服务。Node 方式使用 Ctrl+C；Docker 方式可用 `docker compose stop quotes`。不要执行 `docker compose down -v`，不要删除原数据卷。
3. 在停止状态下额外复制完整数据目录或备份命名卷；`.env` 单独由商家安全保存。不要只复制运行中的 `quotes.sqlite` 文件，WAL 中可能还有最新数据。
4. 将旧版源码、旧版 JSON、冷备份和配置副本分别标明日期，并至少保存一份异机副本。

**升级：**

1. 将新版本解压到独立目录，保留旧版；核对发行说明与迁移要求。
2. 在独立数据副本或新测试卷上先启动新版本，完成一份虚构报价、PDF、跟进、重启和恢复检查。
3. 检查通过后再切换正式服务。升级后如有新录入，应立即再备份，避免回滚时遗漏。

**回滚：**

1. 停止新版本，将出现问题时的当前状态另行备份，不覆盖升级前的文件。
2. 使用保留的旧版源码，指向新的独立恢复目录或新命名卷。
3. 恢复升级前由旧版本导出的 JSON；若使用冷备份，则只在已停止的服务上恢复完整匹配文件，不混用升级后的数据库。
4. 核对客户、报价金额、中文 PDF 和跟进，再重启检查。确认后才切换手机访问入口并继续录入。
5. 记录故障、实际回滚版本和是否需要手工补录升级后的业务。不能假设新版数据可直接交给旧版本读取。

Docker 命名卷的冷备份与恢复应由安装人员按交付环境完成，并把实际卷名、操作步骤和验证结果记录下来。源码 ZIP、镜像和容器本身都不替代业务数据备份。
